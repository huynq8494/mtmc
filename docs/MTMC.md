# MTMC - Multi-Target Multi-Camera Tracking on a 2D Warehouse Map

This document explains everything in `~/study/mtmc/`: what the program does, the math behind it, every file and
function, every tunable parameter, how the camera config is parsed, what has been verified, and what is still weak.

[TOC]

---

## 1. What the application does

Input: 12 synchronized videos (`videos/camera01.mp4` ... `camera12.mp4`) recorded in an NVIDIA Isaac Sim warehouse.
Each video is 1920x1080, 50 fps, 755 frames (about 15.1 s). About 10 people walk in the warehouse.

Output: a top-down 2D map that shows, for every moment in time,

- the walkable floor rectangle,
- the 12 cameras with their field-of-view wedge,
- each tracked person as a coloured dot with a numeric ID and a fading trail.

The map is written to `out.mp4` and can be shown live with `--show`.

The core idea is **ground-plane triangulation**: a person's feet touch the floor (z = 0), and a camera pixel
is a ray in 3D. Intersecting the ray through the foot pixel with the floor gives the person's (x, y) on the map.
Because the 12 cameras overlap, the same person is seen several times; those observations are fused and tracked.

## 2. Pipeline overview

```
 videos/cameraNN.mp4  (N = enabled cameras)
        |
        |  main.py: grab (step-1) frames, read 1 frame per camera
        v
 +-----------------+   detector.py
 | YOLO11n         |   person boxes (x1,y1,x2,y2,conf)       per camera, batched
 | OSNet x0.25     |   512-d appearance embedding per crop   per box
 +-----------------+
        |
        v   foot pixel = (box centre x, box bottom y)
 +-----------------+   geometry.py  Camera.ground()
 | pixel -> ray    |   ray (camera frame) -> world frame with R
 | ray x floor z=0 |   world (x, y) + distance from camera
 +-----------------+
        |
        v   filters in main.py
   drop if: box touches bottom edge | ray misses floor | point outside floor box (+1 m)
        |
        v
 +-----------------+   tracker.py  fuse()
 | cross-camera    |   cluster points of the same person from different cameras
 | fusion          |   -> one (x, y, embedding, cameras) per person per time step
 +-----------------+
        |
        v
 +-----------------+   tracker.py  Tracker.step()
 | Kalman + Hungar.|   stable IDs, confirm/delete logic, floor clamp
 +-----------------+
        |
        v
 2D map (main.py draw())  ->  out.mp4  and optional live window
```

## 4. Installation and running

The environment is managed by `uv` and lives in `.venv/` (Python 3.11).

```bash
cd ~/study/mtmc
uv sync                      # creates .venv from pyproject.toml / uv.lock
uv run main.py --check       # camera diagnostic, no video processing
uv run main.py               # all 12 cameras, auto CPU/GPU, writes out.mp4
```

Dependencies: `numpy`, `scipy`, `opencv-python`, `torch`, `torchvision`, `ultralytics`.
`torchreid` is deliberately **not** installed (its build failed here); only `osnet.py` is vendored.
`matplotlib` is needed only for `tools/plot2D.py` and is not in `pyproject.toml`.

### Command line options

| Option | Default | Meaning |
|---|---|---|
| `--cams` | `1-12` | Enabled cameras. Ranges and lists: `1-12`, `1,7,8,10,11`, `9-12`. |
| `--device` | `auto` | `auto` uses CUDA if `torch.cuda.is_available()`, else CPU. Or force `cpu` / `cuda`. |
| `--step` | `5` | Process every Nth frame. Videos are 50 fps, so `5` gives 10 map frames per second, `10` gives 5. |
| `--max-frames` | `0` | Stop after N processed frames (0 = whole video). |
| `--imgsz` | `960` | YOLO input size. Larger finds smaller/farther people but is slower. |
| `--hfov` | from config | Override horizontal field of view in degrees. |
| `--out` | `out.mp4` | Map video file. |
| `--show` | off | Live window; press `q` to quit. |
| `--debug` | off | Draw raw points on the map and write `debug_cams.mp4` (see section 11). |
| `--check` | off | Print camera pose diagnostic and exit. |

Typical commands:

```bash
uv run main.py --cams 9-12 --device cpu --step 10 --debug --show   # the south-east rectangle only
uv run main.py --cams 1,7,8,10,11                                   # fewer cameras, faster
uv run main.py --hfov 55 --check                                    # try another field of view
```

Messages like `QFontDatabase: Cannot find font directory ... cv2/qt/fonts` when using `--show` are harmless
OpenCV/Qt warnings about missing fonts.

## 5. Coordinate systems and conventions

### 5.1 World frame
Right-handed, metres. X and Y lie on the floor, **Z is up**. The floor is z = 0. All cameras are mounted at z = 3 m.

### 5.2 Camera positions (from `configs/camera_properties.txt`, `xformOp:translate`)

| Cam | x | y | Wall / role |
|---|---|---|---|
| 1-6 | -22.84, -17.89, -12.94, -7.98, -3.02, 1.94 | 30 | north wall, evenly spaced |
| 7 | 5 | 30 | north-east corner |
| 8 | -26 | 30 | north-west corner |
| 9 | -26 | 8.5 | west wall, middle |
| 10 | -26 | -23 | south-west corner |
| 11 | 5 | -23 | south-east corner |
| 12 | 5 | 8.5 | east wall, middle |

Seen from above with Y pointing up on the map:

```
   8 (-26,30)   1  2  3  4  5  6   7 (5,30)
   +---------------------------------+
   |                                 |
   9 (-26,8.5)                  12 (5,8.5)
   |                                 |
   |                                 |
   +---------------------------------+
  10 (-26,-23)                  11 (5,-23)
```

### 5.3 Walkable floor (the "ground limit")
The bounding box of all camera positions defines the floor rectangle (here set by the corner cameras 7, 8, 10, 11):

```
x in [-26, 5]     y in [-23, 30]       (31 m x 53 m)
```

`config.py` computes `XMIN, XMAX, YMIN, YMAX` from the parsed camera positions, so if you move a camera and
re-parse the export, the limit follows automatically.

### 5.4 Camera frame and orientation
The convention is the one used by USD / Isaac Sim cameras:

- the camera looks along its local **-Z** axis,
- local **+Y** is the image "up" direction,
- local **+X** is the image "right" direction.

Orientation is the exported unit quaternion `xformOp:orient` = (w, x, y, z). `parse_camera_config.py` converts it to the
camera-to-world rotation matrix `R` (stored as `rotation` in `configs/cameras.py`). A camera direction in the world is
`R @ d_camera`. No Euler angles and no manual pose overrides are used.

Resulting directions (from `--check`):

- Cameras 1-6: `fwd = (0, -0.97, -0.26)`, looking south (into the warehouse from the north wall), 15 degrees below the horizon.
- Cameras 7 and 8: `fwd = (-0.97, -0.26, 0)` (west) and `(+0.97, -0.26, 0)` (east).
- Cameras 9-12: diagonal, `fwd = (+-0.71, +-0.71, 0)`, all upright (`up.z = +1`).
- `fwd = R @ [0, 0, -1]` is the viewing direction; `up = R @ [0, 1, 0]`. If `up.z < 0` the image is upside down.
  `--check` flags this as `UPSIDE-DOWN`.

### 5.5 Image frame
Pixel `(u, v)`, origin top-left, `u` to the right, `v` downwards. Size `W x H` = parsed `resolution` (1920 x 1080 by default), principal point at the image centre.

### 5.6 Map frame
`main.py` draws at 15 pixels per metre with a 40 px margin; world Y is flipped so north is up:

```
px = 40 + (x - XMIN) * 15         py = 40 + (YMAX - y) * 15
```

The map image is 545 x 875 pixels.

## 6. Camera model and the pixel-to-floor math (`geometry.py`)

### 6.1 Intrinsics
Pinhole camera, no lens distortion, square pixels, principal point at the centre.

```
HFOV = 2 * atan( aperture / 2 / focal_length ) = 2 * atan( 20.955 / 2 / 18.15 ) = 60.0 deg
F    = (W / 2) / tan(HFOV / 2)                                           = 1663 px
```

The Isaac Sim default camera has a 20.955 mm horizontal aperture and an 18.15 mm focal length, which gives 60 degrees.
The video files themselves carry no camera data, so this is an assumption. It was **validated** by checking that
cameras 9, 10, 11 and 12 agree on where people stand (see section 12.2). Override with `--hfov`.

### 6.2 `Camera.ground(uv)` - pixel to floor point
For a pixel `(u, v)`:

1. Ray in the camera frame: `d_cam = ( (u - W/2)/F , -(v - H/2)/F , -1 )`. The minus on the second term is
   because image `v` grows downward while camera `+Y` is up. The `-1` is "forward" (-Z).
2. Rotate into the world: `d = R @ d_cam`, then normalise.
3. The ray is `P(t) = C + t * d` with `C` the camera position. The floor is `z = 0`, so
   `t = -C.z / d.z`. This only makes sense if the ray points downward (`d.z < 0`); otherwise the pixel sees sky/horizon
   and the result is marked invalid.
4. Floor point: `(C.x + t*d.x , C.y + t*d.y)`. The distance `t` is returned too.
5. Points farther than `MAX_RANGE = 80 m` are marked invalid.

Return values: `(xy, ok, t)`. The code is vectorised over many pixels.

Why the foot point: the bottom-centre of the person box is where the person touches the floor. Using the box centre
would put the point at hip height and shift the projection away from the camera.

**Sensitivity (important to understand errors):** with a camera 3 m high, a pixel near the horizon corresponds to a
very long ground distance, so a few pixels of box error or a small error in FOV/tilt becomes metres on the map.
This is why far detections are weighted less in the fusion step (section 9).

### 6.3 `Camera.project(xyz)` - world to pixel
The inverse operation (world point to pixel and an "inside image" mask). It is used only by `--check`
to find which parts of the floor each camera can see.

### 6.4 `check(ids)` - the `--check` diagnostic
For every enabled camera prints position, viewing direction `fwd`, `up.z`, the floor point hit by the bottom-centre of
the image, and the fraction of the floor grid (1 m spacing) inside the image. It prints flags:

| Flag | Meaning |
|---|---|
| `UPSIDE-DOWN` | `up.z < 0`, the image is flipped. |
| `NO-GROUND-AT-BOTTOM` | the bottom of the image never reaches the floor. |
| `LOOKS-OUTSIDE-BOUNDS` | the bottom-centre hit is more than 2 m outside the floor rectangle. |
| `SEES-<5%-OF-FLOOR` | the camera sees almost no floor. |

Finally prints how much of the floor is covered by at least one and at least two cameras
(currently 100 % and 100 % at 60 degrees HFOV).

## 7. Camera configuration parsing (`parse_camera_config.py`)

All camera data comes from the Isaac Sim export `configs/camera_properties.txt`; there are no manual pose fixes.

```
python parse_camera_config.py                    # -> configs/cameras.py (default)
python parse_camera_config.py --format json      # -> configs/cameras.json
python parse_camera_config.py -i props.txt -d defaults.json -o out.py --strict --quiet
uv run main.py --parse-cameras [--camera-props P] [--camera-defaults D]   # parse, then run
```

- Properties missing from the export (here: aperture, resolution, and `centerOfInterest` of cameras 3-6) are taken from
  `configs/camera_defaults.json`, and one warning per property is printed. `--strict` turns this into an error.
- Derived values: rotation matrix, `forward`, `up`, `hfov_deg`, `focal_px`.
- The old Euler-angle files were removed. The exported quaternion of camera 12 gives `fwd = (-0.71, -0.71, 0)` and
  `up.z = +1`, i.e. the pose that used to be hand-corrected; the Euler file had been wrong for camera 12 only.

**Not verified:** cameras 1-8 were never checked against the images. Cameras 9-12 agree with each other to about 0.4 m
(section 12.2). Cameras 7 and 8 are the ones with the most rejected detections (camera 7: 46 %); this is mostly because
people's feet are cut off by the bottom image edge, but a small pose error cannot be excluded (see section 13).

## 8. Detection and appearance embedding (`detector.py`)

### 8.1 Class `Detector(device, imgsz=960, conf=0.35)`

- `device`: `auto` picks CUDA when available. Everything (YOLO and OSNet) runs on the same device.
- **YOLO11n** (`yolo11n.pt`): the fastest YOLO11 size. Only class 0 (person) is requested, confidence threshold 0.35.
  On CUDA it runs in half precision (`half=True`); on CPU it runs in float32.
- **OSNet x0.25**: a small person re-identification network. It is built with `num_classes=4101`
  (the MSMT17 training identities) and the weights are loaded from `models/osnet_x0_25_msmt17.pth`. The classifier is
  not used; in eval mode the network returns the 512-dimensional feature.

### 8.2 `__call__(frames)`
Input: list of BGR frames (one per enabled camera). Steps:

1. One batched YOLO call for all frames. Boxes are in pixels of the original 1920x1080 image.
2. For every box, crop the frame, convert BGR to RGB (`[..., ::-1]`), resize to **128 x 256** (width x height).
3. Normalise with ImageNet mean/std, stack all crops of all cameras in a single tensor, and run OSNet once.
4. L2-normalise the 512-d vectors so that a dot product equals cosine similarity.
5. Split the results back per camera.

Output: for each frame a tuple `(boxes (N,5) [x1,y1,x2,y2,conf], embeddings (N,512))`.

## 9. Cross-camera fusion (`tracker.fuse`)

Goal: turn many single-camera observations of one person into one measurement.

Input: list of `(xy, embedding, camera_id, range)`.

Algorithm (greedy clustering):

1. Sort observations by range, **nearest camera first**. Near observations are the most precise (see 6.2).
2. For each observation, look for an existing cluster whose current position is within
   `FUSE_D + 0.03 * range` metres (0.8 m + 3 % of range, so far observations are allowed more disagreement),
   **and which has no observation from the same camera yet** (one person cannot appear twice in one camera view).
3. If found, add it to the cluster and recompute the cluster position as a weighted mean, weights `1 / range^2`.
   Otherwise start a new cluster.
4. Cluster embedding = mean of the member embeddings, re-normalised.

Output: list of `(xy, embedding, [camera ids])`. The number of camera ids is a confidence indicator: a cluster seen by
several cameras is far more trustworthy than a single observation.

Limitations: it is a greedy algorithm, so two people standing closer than the threshold can merge, and a bad single
observation can be glued to the wrong person. Appearance is **not** used here, only distance.

## 10. Tracking (`tracker.py`)

### 10.1 `Track`
State `x = [px, py, vx, vy]` (floor position and velocity), covariance `P`, plus the mean appearance embedding, the number
of `hits`, the number of consecutive misses `miss`, the cameras that saw it last (`cams`), `confirmed` flag, and the
`trail` of positions.

- `predict(dt)`: constant velocity model. `F` adds `dt * v` to the position. Process noise
  `diag(0.05, 0.05, 0.5, 0.5) * dt`. Increments `miss`.
- `update(xy, emb, cams)`: Kalman update with measurement noise 0.3 on each axis. After the update the position is
  clamped into the floor rectangle. The embedding is blended: `0.9 * old + 0.1 * new`. `miss` returns to 0.

### 10.2 `Tracker.step(fused, dt)` - one time step
`dt = step / fps` seconds (for `--step 10` that is 0.2 s).

1. **Delete stale tracks**: tracks with `miss * dt > MAX_MISS_S` (3 s) are removed. This frees slots.
2. **Predict** all remaining tracks and clamp them to the floor.
3. **Build a cost matrix** tracks x fused detections:
   - `gate = GATE + 1.0 * miss * dt` (1.5 m, growing by 1 m per second of being lost);
   - `d = distance / gate`; if `d >= 1` the pair is forbidden (cost 1000);
   - otherwise `cost = d + 0.5 * (1 - cosine_similarity(track embedding, detection embedding))`.
   So geometry decides the gate, and appearance only adds a smaller preference between candidates.
4. **Hungarian assignment** (`scipy.optimize.linear_sum_assignment`) gives the globally cheapest one-to-one matching;
   pairs that hit the forbidden cost are dropped.
5. **Update** matched tracks. For unmatched detections **create a new track** if fewer than `PEOPLE` (10) tracks exist;
   otherwise the detection is ignored.
6. **Confirm**: a track becomes `confirmed` once it has `hits >= CONFIRM` (3) or was seen by 2 or more cameras at the
   same time. Once confirmed it stays confirmed.
7. **Return** only tracks that are confirmed **and** matched in this very step (`miss == 0`).

Consequences you will see on the map:

- A person who is not detected for a moment simply disappears from the map until detected again (up to 3 s, after which
  the track is deleted and a later detection may get a **new ID**). The tracker does not draw predicted positions of
  lost tracks.
- IDs are never reused; `next_id` only increases. So after a track is deleted, the same real person can show up as
  ID 11, 12, ... Only 10 tracks can be alive at once.

Why confirmation exists: before it was added, every single (possibly wrongly projected) detection in the first frame
became a permanent track, filled all 10 slots, and the real people in the south-east were never tracked.

## 11. The map and debug output (`main.py`)

### 11.1 Main loop
For each iteration:

1. For every enabled camera, `grab()` (skip) `step - 1` frames and `read()` one. If any video ended, stop.
2. Run the detector on all frames.
3. For each camera: compute foot points, project to floor, apply the filters below.
4. Fuse, track, draw, write.
5. Print a progress line, update statistics.

### 11.2 Filters on every detection (this enforces the ground limit)
```python
ok &= box_bottom < H - 4                  # foot is visible, box not cut by the image bottom edge
good = ok & inside(xy, margin=1.0)        # ray hits the floor, and lies within the floor box +/- 1 m
```
- **Bottom-cut boxes** are rejected because if the feet are outside the image, the bottom of the box is not the foot and
  the projection would be too close to the camera.
- **Out-of-floor points** are rejected: they are errors (a wrong pose, a reflection, a person detected in a poster...).
  The 1 m margin tolerates box jitter near walls.

### 11.3 Four layers of protection for "nobody leaves the floor"
1. Detections whose floor point is outside the rectangle (+1 m) are dropped.
2. Predictions are clamped into the rectangle (`config.clamp`).
3. Updated Kalman states are clamped as well.
4. At the end of the run `main.py` counts track positions outside the rectangle and `assert`s the count is zero.

Honest note: because of layers 2 and 3 the final assertion cannot fail by construction; the meaningful evidence that
the geometry is right is the per-camera rejected counts (see section 12), not that assertion.

### 11.4 Map drawing
- Dark background, 5 m grid lines, grey rectangle for the floor.
- Cameras: orange dot with number, a thin wedge of radius 4 m and angle `HFOV` showing the viewing direction.
- People: coloured dot, white ID text, polyline trail with the last 40 positions. Colours come from 10 evenly spaced hues
  and are chosen with `(id - 1) % 10`, so ID 11 shares the colour of ID 1.
- Header text: time in seconds, processed frame count, number of visible people, number of enabled cameras.

### 11.5 `--debug`
- Small grey dots on the map for every accepted raw single-camera floor point (before fusion). Where grey dots from
  different cameras clump together, those cameras agree. Grey dots that are far from every coloured dot are noise.
- `debug_cams.mp4`: a 4-column grid of 480x270 thumbnails of all enabled cameras, with person boxes
  (**green = accepted, red = rejected**) and the camera number.

### 11.6 Statistics printed at the end
```
processed=75 unique_ids=[1, ..., 11] raw_points_rejected_outside_ground=215 track_positions_outside_ground=0
per-camera [dets, rejected]: {1: [94, 14], ..., 7: [293, 135], ..., 12: [148, 0]}
```
`rejected` counts all rejected boxes (bottom-cut, no floor hit, outside floor). Large numbers on one camera mean its
pose, field of view or framing needs attention.

## 12. What was verified and how

### 12.1 Geometry checks
- `--check` at 60 degrees: no camera is flagged `UPSIDE-DOWN` or `LOOKS-OUTSIDE-BOUNDS`; 100 % of the floor is seen by at
  least one camera and 100 % by at least two. Every camera looks into the warehouse, none looks outward.
  Floor fraction seen per camera: cams 1-6: 57-73 %, cams 7-8: 27 %, cam 9 and 12: 40 %, cams 10-11: 65 %.

### 12.2 Field of view (cross-camera agreement test)
Using one synchronised frame from cameras 9, 10, 11, 12 (the south-east rectangle with 2 people), the mean distance from
each observation to the nearest observation of another camera was measured for several FOV values:

| HFOV | Mean cross-camera distance |
|---|---|
| 47.2 deg (my first guess) | 9.5 m |
| 55 deg | 3.1 m |
| **60 deg** | **0.38 m** |
| 65 deg | 3.1 m |

At 60 deg all four cameras place the two people at about (-11.2, -10.5) and (-6.7, -10.8) m. This is the main evidence
that the 60 degree model and the poses of cameras 9-12 are consistent.

### 12.3 Full run (all 12 cameras, CPU, `--step 10`, 75 map frames)
- 11 distinct IDs were created for about 10 people, so at least one person received a second ID after a track was
  deleted (not checked which). No track position is outside the floor.
- Rejected detections per camera: cams 1-6: 9-22 each, **cam 7: 135 of 293**, cams 8-12: 0.
- Speed on this 32-core CPU machine: about 0.6 s per processed frame set (12 cameras), so a 15 s video at `--step 10`
  takes about 45 s. GPU path implemented but **not tested** (no GPU on this machine).

### 12.4 What has not been verified
- The output videos were not inspected visually by me; the results above come from printed numbers.
- Identity correctness over time (does ID 5 always follow the same person?) was not measured; there is no ground truth.
- Poses of cameras 1-8 were not cross-checked against images.

## 13. Known weaknesses and suggested next steps

| Issue | Cause | Suggestion |
|---|---|---|
| Camera 7 rejects ~46 % of boxes | People walk through the lower image edge, so the box bottom is cut off | Accept bottom-cut boxes but estimate the foot from the box height (person height ~1.7 m) instead of dropping them. |
| Many north-side tracks are seen by only one camera | Cameras 1-6 (tilted 15 deg below horizon) see people at long range and from the side | Cross-check poses of cameras 1-8 the same way as 9-12; consider a smaller `FUSE_D` growth with range. |
| People vanish for a moment and may get a new ID | Missed detections; lost tracks are not drawn; tracker deletes after 3 s | Draw predicted positions in a dimmer colour; increase `MAX_MISS_S`; use appearance to re-link after deletion. |
| ReID is only a tie-breaker | Weight 0.5 relative to a normalised distance, embeddings blended slowly; simulated avatars may look alike | Evaluate embedding quality on your data; raise the weight if people are visually distinct. |
| Greedy fusion can merge close people | Distance-only clustering | Add an appearance term to the cluster distance, or use Hungarian between cameras. |
| Fixed camera model | No lens distortion, FOV assumed | Get real intrinsics from Isaac Sim (`Camera` prim: focal length, horizontal aperture) and put them in `configs/camera_properties.txt` / `camera_defaults.json`. |
| Speed on CPU | 12 videos at 1920x1080 and 960 px YOLO | Use `--step 10`, `--imgsz 640`, fewer cameras, or a GPU. |

## 14. Parameter reference (`config.py`)

| Name | Value | Meaning | Effect if increased |
|---|---|---|---|
| `W, H` | 1920, 1080 | Video size | - |
| `HFOV` | 60 deg | Horizontal field of view (from 18.15 mm lens, 20.955 mm aperture) | Places points farther/closer; a wrong value gives large errors at long range |
| `F` | 1663 px | Focal length in pixels (derived) | - |
| `MAX_RANGE` | 80 m | Ignore ground hits farther than this | More far (noisy) points are accepted |
| `XMIN..YMAX` | -26..5, -23..30 | Floor box = bounding box of all camera positions | - |
| `PEOPLE` | 10 | Max simultaneous tracks | More ghost tracks possible |
| `FUSE_D` | 0.8 m | Cross-camera merge distance (+3 % of range) | More merging, more false merges |
| `GATE` | 1.5 m | Track-to-detection association gate | Follows fast motion, more ID swaps |
| `CONFIRM` | 3 | Frames before a track is shown (or 2+ cameras) | Fewer ghosts, slower start |
| `MAX_MISS_S` | 3 s | Delete a track after this long without detection | IDs survive longer gaps, ghosts linger |

Other constants in code: YOLO confidence 0.35 (`detector.py`), crop size 128x256, Kalman process noise
`diag(.05,.05,.5,.5)*dt` and measurement noise 0.3 (`tracker.py`), appearance weight 0.5, embedding blend 0.9/0.1,
map scale 15 px/m, trail length 40 (`main.py`).

## 15. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| People appear in the wrong part of the map | Wrong camera pose or FOV. Run `--check`, then `--debug --cams <few cameras>` and compare grey dots between cameras. |
| A camera shows nothing in the map | All its boxes rejected: look at the red boxes in `debug_cams.mp4` and the per-camera counts. |
| Fewer than 10 people visible | People hidden/lost for a moment (section 10.2) or detection threshold too high; try `--imgsz 1280` or lower `conf` in `Detector`. |
| More than 10 IDs in the summary | Track deleted after 3 s and a new one created. Increase `MAX_MISS_S`. |
| Very slow | Use `--step 10`, `--cams` subset, or `--device cuda`. |
| `ModuleNotFoundError: config` when running a helper script from another folder | Run from `~/study/mtmc` or set `PYTHONPATH=.`. |
| Cannot open window | No display; omit `--show`. |
| First run tries to download `yolo11n.pt` | Needs internet access once (5 MB). |
